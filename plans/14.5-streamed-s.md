# Plan — fix DESIGN §14.5: `streamed_s` counts a silent source as streamed

**For:** an agent picking this up cold.
**Target file:** `src/pimd_classviz.py` (currently v1.75) — one file, no firmware change.
**Read first:** `CLAUDE.md` (how to behave here), then `DESIGN.md` §14.5 and §9.
**Status:** not started. This document is a brief, not a record — delete it once the fix lands.

---

## 1. The defect

`streamed_s`, the soak-accounting figure ClassViz writes into every session dump, measures
**wall-clock since the streaming run armed**, not the arrival of data. A firmware source that goes
quiet *without closing the serial port* is therefore invisible to it.

**Evidence — `src/data/sessions/session_20260812_150333.csv`.** The firmware latched `LOCKOUT` at
15:58:04 and stopped emitting sweeps. The dump went on writing

```
streamed_s=7314, stalled_s=0
streamed_s=7374, stalled_s=0
streamed_s=7434, stalled_s=0   … until 17:08
```

**70 minutes of zero data counted as soak, with the stall detector never firing once.**

This matters because effective soak is defined as `streamed_s - stalled_s`, and soak is what the
thermal-drift work reasons about (DESIGN §3: band 0 moves −7.6 % over warm-up). An overstated soak
silently corrupts that reasoning, and it does so precisely on the long unattended run the accounting
exists to watch.

**This is NOT the v1.74 bug.** v1.74 fixed *arming* — `_begin_stream_run()` never being called on
the Load & Run path. That is fixed and verified. This is a defect in what the correctly-armed
counter **measures**. Do not "fix" it by revisiting `_begin_stream_run()`.

---

## 2. Root cause

Two functions, and the asymmetry between them is the whole bug.

`_streamed_s()` (~line 8300) is **wall-clock driven** — it grows whether or not anything arrives:

```python
total = self._streamed_total_s
if self._stream_run_start_wall is not None:
    total += time.time() - self._stream_run_start_wall
```

`_note_frame_gap(fw_time_ms, wall_ts)` (~line 8326) is **arrival driven** — it is called only from
the `W` handler (~line 7606), and it detects a gap by comparing the *firmware's* elapsed-ms field
between two frames that both actually landed:

```python
prev = self._last_fw_time_ms
self._last_fw_time_ms = fw_time_ms
if prev is None or fw_time_ms < prev:
    return
gap_s = (fw_time_ms - prev) / 1000.0
if gap_s < FRAME_GAP_WARN_S:      # 2.0
    return
self._stall_total_s += gap_s
```

So the stall detector is **retrospective**: it can only charge a gap once the stream *resumes* and a
frame lands carrying a jumped `fw_time_ms`. If the stream never resumes — lockout, cable pulled, USB
wedged, MCU crash — no frame ever lands, `_note_frame_gap` is never called, and `_stall_total_s`
stays at 0 forever while `_streamed_s()` keeps climbing on the wall clock.

Using firmware time rather than PC wall time was a deliberate and correct choice (see the docstring:
it answers "did the MCU stop emitting", and survives host-side scheduling jitter). **Keep it.** The
fix adds a second, wall-clock detector for the case the first cannot see; it does not replace it.

---

## 3. The trap: do not double-count

The obvious implementation — accumulate wall-clock silence into `_stall_total_s` — **double-counts
every recoverable stall**. Consider a 300 s silence that then resumes:

1. the new watchdog charges ~300 s of silence while it is happening, then
2. the first frame to land afterwards carries a `fw_time_ms` jump, and `_note_frame_gap` charges the
   same ~300 s again.

Result: `stalled_s ≈ 600` against 300 s of real silence, and effective soak goes *negative* — the
same class of nonsense as the v1.74 symptom, reintroduced from the other side.

**Any accepted solution must handle this explicitly**, and must be tested against the *recovering*
case, not only the terminal one. Two workable strategies:

- **(A) Suppress on resume.** The watchdog records the wall interval it has already charged for the
  current silence. When `_note_frame_gap` next fires, subtract what was already charged and add only
  the remainder (floor at 0). Keeps one accumulator; needs the bookkeeping to be exactly right.
- **(B) Separate accumulators.** Watchdog writes `silent_s`, `_note_frame_gap` keeps `stalled_s`
  untouched, and the two are reconciled at read time (a silence that resumed is *already* covered by
  the fw-time gap, so `silent_s` only contributes where no resuming frame ever arrived). Changes the
  `# soak:` line's field set — see §6 on compatibility.

**(B) is recommended.** It leaves the existing, well-tested fw-time path completely untouched, keeps
the subtraction visible and reversible in the dump (the stated design intent of `_soak_fields()`),
and makes the two failure modes distinguishable after the fact instead of merging them into one
number. Justify whichever you pick in the CHANGELOG entry.

## 4. Where to hook the watchdog

**There is already a 1 Hz timer — use it, do not add a second.** `self._rate_timer` (~line 1069)
fires `_update_rate()` every 1000 ms, and that function already carries `_update_pack_v_age()` and
the periodic `# soak:` emit for exactly this reason (see its v1.64/v1.66 comments). The silence
watchdog belongs on the same tick.

**You will need a frame-arrival wall timestamp — it does not exist yet.** `_note_frame_gap` receives
`wall_ts` but only stores it as `_stall_last_wall` (and only when a gap is detected). Add something
like `self._last_frame_wall`, set unconditionally in the `W` handler (~line 7606), initialised in
`__init__` near `self._fps_hz` (~line 848), and — importantly — reset in `_begin_stream_run()`
alongside `_last_fw_time_ms`, so a new run does not inherit the previous run's arrival time.

**Guards the watchdog must respect**, or it will charge silence that is not a defect:

- `self._stream_run_start_wall is not None` — not armed means not streaming (this is the v1.74
  invariant; honour it).
- `self.pb_start.text() == 'Running'` — a deliberately stopped stream is not a stall. Note
  `_update_rate` already tests this for the Rate readout.
- `self._session_paused` — a paused dump is not describing the rig (the codebase applies this rule
  consistently; follow it).
- Grace period before charging anything. `FRAME_GAP_WARN_S = 2.0` is the existing threshold for "a
  gap worth recording" and reusing it keeps one concept; but note the watchdog runs at 1 Hz on a
  16 Hz stream, so consider whether 2 s is too tight against normal jitter. If you introduce a new
  constant, name it and comment *why* it differs.

## 5. Behaviour to implement

1. **Charge silence while it is happening**, at 1 Hz, once past the grace period.
2. **Write a durable record into the dump** so after-the-fact analysis can mask the window rather
   than infer it — matching how `_note_frame_gap` writes `# stall:` lines. Use a distinct marker
   (e.g. `# silence:`) so the two mechanisms stay distinguishable. Follow the existing
   write-then-flush pattern and the `_recording and _session_file and not _session_paused` guard.
3. **Surface it in the UI, latched.** `_update_rate` already latches stall counts precisely because
   an instantaneous readout "is exactly what failed to raise the alarm on 2026-07-29". A silent
   stream must say so on the Rate readout and must not clear itself. Check whether
   `_window_block_reason == 'stalled'` (drives "STREAM STALLED" on the σ / scale labels) should also
   be driven from silence — probably yes, and cheap.
4. **Close the run out cleanly** at `stream-stop` so the banked `_streamed_total_s` is not inflated.

**Special case worth handling directly: lockout.** The firmware prints `LOCKOUT:` and ClassViz
already parses it and sets `_pack_lockout` (~lines 7533 / 7567). A latched lockout means the source
will *never* resume without a power cycle, so it is knowable immediately rather than after a
timeout. Consider ending the streaming run's soak accounting the moment lockout latches. This is the
exact 2026-08-12 case. It is a complement to the watchdog, not a substitute — the watchdog is what
catches a pulled cable, a wedged USB or a crashed MCU, none of which announce themselves.

## 7. Test plan

There is no unit-test harness in this repo, so tests are offscreen-driver scripts. `QT_QPA_PLATFORM=
offscreen` works for constructing `MainWindow` and driving methods directly — verified.

**Must cover all four, and the recovering case is the one that catches a bad fix:**

| # | Scenario | Expected |
|---|---|---|
| 1 | **Terminal silence.** Arm a run, feed `W` frames, then stop feeding entirely. | `stalled_s`/`silent_s` grows with wall time; effective soak stops growing. This is the 2026-08-12 case. |
| 2 | **Recovering silence.** Feed frames, go quiet ~300 s, then resume with a correspondingly jumped `fw_time_ms`. | Silence charged **once**, not twice. Effective soak never negative. |
| 3 | **Normal streaming.** Frames at ~16 Hz throughout. | `silent_s` stays 0; no `# silence:` lines; no UI warning. |
| 4 | **Deliberate stop / pause.** Stop the stream, or pause the session, then wait. | Nothing charged, no warning — a stopped stream is not a stall. |

**Regression check against real data:** re-derive the figures for
`session_20260812_150333.csv` and confirm effective soak now ends at the lockout (15:58:04) rather
than at 17:08. Also re-check `session_20260812_150333`'s companion sessions for no change on runs
that never went silent.

**Acceptance:** all four scenarios pass; scenario 2 shows no double-count; the four GUIs still
launch offscreen; `python3 -c "import ast;ast.parse(open('src/pimd_classviz.py').read())"` clean.
